# архитектура «Сна Борхеса»

> **статус:** документ фиксирует границы текущего клиента и контракт следующих фаз. Сейчас репозиторий остаётся статическим одиночным приложением. Сетевые компоненты, аккаунты, Workers, Durable Objects и D1 ещё не реализованы. Физические проходы между комнатами построены.

## 1. основной принцип

**каталог определяет книги, мир размещает их, сервер синхронизирует только людей.**

Три класса данных имеют разные источники истины:

| данные | источник истины | можно ли менять без новой версии |
| --- | --- | --- |
| страницы и идентичность книги | детерминированный каталог v3 | нет |
| физическое повторение книги и room id | детерминированное размещение w3 | нет |
| присутствие, закладки и заметки | будущий сервер пользовательских данных | да, по правилам продукта |

Серверу не нужна база текстов или геометрии. Любой клиент воспроизводит их локально по versioned-адресам.

## 2. каталог v3 и размещение w3

### v3

v3 — конечная биекция между индексами `0…B−1` и всеми полными 410-страничными книгами 29-знакового алфавита. Существующие записи вида

~~~
v3;<catalogue-room-index hex>;<wall>;<shelf>;<volume>;<page>
~~~

остаются неизменными.

### w3

w3 — безграничное физическое пространство. Точные BigInt q/r/level обратимо дают `worldRoomIndex = n`; все n валидны. Один физический слот получает каталоговый индекс:

~~~
i = (3840n + s + WORLD_BOOK_OFFSET) mod B
~~~

Каноническая физическая запись:

~~~
w3;<world-room-index lowercase hex>;<wall>;<shelf>;<volume>;<page>
~~~

Для самой комнаты используется префикс этой записи: `w3;<world-room-index>`. Декоративный h-тег не является ключом и не участвует в протоколах.

`WORLD_BOOK_OFFSET` фиксирует начальную раскладку: манифест находится в `w3;0;2;2;13;197`. Старые w2/w1-записи декодируются своей замороженной 640-томной раскладкой.

### режимы открытия

- нажатие e открывает физический том текущей комнаты и знает оба контекста: w3-место и v3-книгу;
- поиск и прямой v3-адрес открывают каталоговую запись, не меняя w3;
- физическая комната меняется пешком через проход, а также явной навигацией к мировому адресу или строкой реестра.

## 3. текущий клиент

Текущие слои репозитория:

Детерминированное ядро лежит в корне и не зависит от клиента:

- `babel-v3.js` — содержимое полного тома и v3-адреса;
- `world-engine.js` — точные координаты, w3-адреса, совместимость w2/w1 и циклический placement;
- `world-model.js` — соседи, карта, exact room record и декоративные теги.

Клиент разложен по слоям:

~~~
src/
  constants.js   размеры комнаты, полок и лимит адреса
  player.js      общее состояние игрока (yaw, pitch, locked)
  audio.js       фоновый дрон
  core/          scene, camera, renderer, общие материалы
  world/         геометрия, построение комнаты, текущая комната
  ui/            reader, catalogue panel, room record, map, hud
  input/         pointer lock, движение, прицеливание
  main.js        связывание слоёв и кадровый цикл
~~~

`main.js` — единственное место, знающее, какая клавиша открывает какую панель. Благодаря этому `input`, `world` и `ui` не импортируют друг друга по кругу. Слой `net/` появится вместе с фазой присутствия.

В основной three.js-сцене одновременно существует одна полная комната и два
настоящих прохода. Все шесть достижимых соседних комнат готовятся короткими
гарантированными задачами, пока игрок ещё находится в гексе, заранее
компилируют портальные материалы и живут в отдельных портальных сценах.
Depth-tested stencil-проёмы не позволяют им просвечивать через стены и
потолок; сами комнаты не участвуют в коллизии и picking основной сцены. Любой
переход — прямой, левый или правый — переносит уже видимый объект комнаты в
основную сцену без повторной сборки. Упрощённых горизонтальных комнат в vista
нет; общей облегчённой геометрией остаются два прохода и дальние этажи стека.

Комната из 3840 томов укладывается в проверяемый бюджет 60 draw calls. Невидимый
портал не отрисовывается благодаря проверке camera frustum. Тома собраны в
`InstancedMesh`; шесть неизменяемых портальных оболочек разделяют уже загруженные
матрицы книг до copy-on-write при принятии комнаты. Обводки слиты в один буфер,
а названия корешков — в один меш на текстурный атлас.
Дальний слой использует непрерывные белые книжные полосы с редким ритмом
корешков, упрощённые балюстрады и не отбрасывает тени. Нормативные размеры и
визуальные инварианты зафиксированы в [контракте геометрии](docs/GEOMETRY_CONTRACT.md).

┌──────────────────────────────────────────────────────────┐
│ static client                                             │

└───────────────────┬───────────────────────┬──────────────┘
                    │ websocket             │ https
┌───────────────────▼────────────────┐ ┌────▼───────────────┐
│ presence service                    │ │ user-data api       │
│ exact w3 room membership            │ │ bookmarks · notes   │

                                                │

~~~

Конкретный провайдер выбирается после прототипа и измерений. Cloudflare Workers, Durable Objects и D1 остаются возможным вариантом, а не текущей зависимостью или заранее доказанной оптимальной схемой.

## 5. presence и произвольные BigInt-координаты

### членство в комнате

При подключении клиент сообщает канонический exact w3 room id. Сервер связывает соединение с этой комнатой. Частые position-пакеты после этого содержат только ограниченные локальные значения внутри гекса: например `x`, `z`, `yaw` и sequence number.

Клиент не отправляет произвольные q/r в каждом тике. Переход комнаты — отдельное редкое событие:

1. клиент сообщает выбранный проход или направление;
2. сервер вычисляет допустимого соседа из текущего exact room id;
3. сервер переводит соединение в новую room membership;
4. локальная позиция сбрасывается к проверенной зоне входа.

Это ограничивает поверхность читов и исключает дорогое повторение гигантских координат в каждом пакете.

### wire-формат

Произвольный BigInt нельзя безопасно помещать в JavaScript Number или фиксированное поле q/r. Допустимые варианты exact room id:

- каноническая UTF-8 строка `w3;<hex>` с ограничением длины сообщения;
- unsigned varint для неотрицательного `worldRoomIndex` плюс явная версия протокола.

Фиксированный бинарный layout применяется только к ограниченным локальным координатам, после серверной валидации их диапазона.

### группировка комнат

Нельзя использовать `Math.floor(q / SECTOR_SIZE)` для BigInt. Если измерения действительно потребуют координатные сектора, применяется точная функция над BigInt:

~~~js
function floorDiv(value, size) {
  const quotient = value / size;
  const remainder = value % size;
  return remainder < 0n ? quotient - 1n : quotient;
}
~~~

`value` и `size` здесь BigInt, а результат сериализуется канонически. Однако секторизация не вводится заранее: сначала измеряется плотность игроков и стоимость room-based membership.

## 6. протокол присутствия

- транспорт: WebSocket или эквивалентный двунаправленный канал;
- client → server: bounded local pose не чаще измеренного лимита;
- server → client: снапшот или delta игроков текущей комнаты;
- room transition: отдельное versioned-сообщение с серверной проверкой соседства;
- reconnect: повторная привязка к последнему подтверждённому w3 room id;
- rate limiting: на соединение, переходы и пользовательские записи.

Сервер является источником истины только по подтверждённой room membership и живой позиции. Он не вычисляет новый текст книги по пользовательскому вводу и не принимает от клиента произвольный телепорт.

## 7. пользовательские данные

Будущее постоянное хранилище содержит только недетерминированные данные:

- закладка каталожной книги v3;
- закладка конкретного физического повторения w3;
- пользовательская заметка;
- публичная запись о находке;
- опциональный профиль.

Поиск содержимого v3 остаётся локальной математической операцией и не переносится в D1. Серверный поиск может относиться только к пользовательским заметкам и публичной ленте.

## 8. безопасность и ограничения

- принимать только канонические versioned-адреса с лимитом размера сообщения;
- не преобразовывать exact room id в Number;
- проверять каждый переход как один допустимый локальный шаг;
- проверять локальную позицию внутри геометрии текущей комнаты;
- ограничивать частоту position, transition и write-запросов;
- разделять детерминированные записи библиотеки и модерируемые пользовательские данные;
- не обещать видимость соседей, пока соответствующая серверная модель не реализована.

## 9. порядок реализации

1. поддерживать замороженные контрольные векторы w3 и совместимость w2/w1;
2. отделить каталоговые записи от физического состояния;
3. добавить локально проверяемый маршрут через проходы;
4. измерить одну комнату и длинную прогулку;
5. прототипировать presence по exact room membership;
6. выбирать секторизацию и провайдера только по результатам нагрузки;
7. добавить пользовательские данные отдельно от книг.
